🌊 ChatCFD 项目详细介绍

一个由大语言模型驱动的智能体（LLM Agent），实现从自然语言 / 学术论文到 OpenFOAM CFD 仿真的端到端自动化

论文：ChatCFD: An LLM-Driven Agent for End-to-End CFD Automation with Structured Knowledge and Reasoning（arXiv: 2506.02019，发表于 Advanced Intelligent Discovery, 2026）

一、项目定位：解决什么问题？

计算流体力学（CFD）长期面临三大门槛：操作复杂（一个 OpenFOAM 算例需要手工编写 0/、constant/、system/ 三个目录下的十余个配置文件）、知识门槛高（需要理解求解器选型、湍流模型、边界条件、离散格式等专业概念）、学习曲线陡峭（新手通常需要数月才能独立完成仿真）。

ChatCFD 的核心思想是：用户只需像聊天一样上传一篇论文或用一句话描述需求，再提供一个网格文件，智能体就能自动完成算例辨识、全部配置文件生成、求解器运行与错误自动修复，把原本数小时到数天的手工配置压缩为一次对话。

论文 PDF → 案例自然语言 → 配置文件自动运行自动纠错OpenFOAM v2406

2.2 双模型分工原理

项目采用 DeepSeek-R1（推理模型）+ DeepSeek-V3（通用模型） 的双通道设计，两个角色各司其职、互为补充：

通道擅长任务典型调用场景
R1 推理通道复杂物理推理、因果分析从论文推断边界条件与物理模型、纠错时分析报错原因并制定修改方案、反思失败经验
V3 执行通道结构化文本生成、格式遵循按模板逐字生成 OpenFOAM 配置文件、输出严格 JSON、将配置转 Markdown 展示

这一分工对应了 CFD 配置的两类本质需求："想清楚"（物理上该怎么设）和"写正确"（语法上怎么写对）。所有调用经 qa_modules.py 统一封装，内置 Pydantic 结构化输出解析、重试机制和逐次 token 消耗日志（qa_logs.jsonl）。

四、核心技术原理

4.1 结构化领域知识库 —— 防止 LLM"幻觉配置"

直接让 LLM 凭记忆写 OpenFOAM 文件，会编造不存在的关键字和文件。ChatCFD 的解法是把 OpenFOAM v2406 的官方知识预先结构化为 5 个 JSON 数据库：

  • final_OF_solver_required_files.json：每种求解器必需哪些配置文件（如 rhoCentralFoam 需要 thermophysicalProperties、fvSchemes…）——保证文件清单完整、不遗漏；
  • final_OF_turbulence_required_files.json：每种湍流模型需要的附加文件；
  • OF_bc_entry.json：合法边界条件类型条目（totalPressure、waveTransmissive、noSlip…）——约束 LLM 只能选用真实存在的 BC；
  • OF_case_dimensions.json：各物理场的量纲（如 p 的 [m2 s-2]），防止量纲写错；
  • processed_merged_OF_cases.json：官方教程全部案例的完整文件内容，作为生成和纠错时的"参考答案"。

生成文件时，LLM 收到的输入 = 教程参考文件 + 论文 RAG 检索片段 + 结构化清单约束，三重锚定使输出既符合 OpenFOAM 语法、又贴合论文参数。

4.2 RAG 论文理解 —— 从学术描述到数值参数

论文中的关键参数（来流速度、总压总温、背压、攻角）散落在全文各处。流程为：PDF 分块（块间距系数 pdf_chunk_d=1.5）→ 嵌入模型 all-mpnet-base-v2 向量化 → FAISS 相似度检索 → 把最相关段落与针对性问题一起交给推理模型。实测中该机制能准确抽取出喷管论文的入口总压 93243.66 Pa / 背压 31073.02 Pa / 300 K 等高精度参数，并映射为正确的 totalPressure/waveTransmissive 边界类型。

4.3 ICOT 迭代纠错 —— 系统可靠性的核心

生成的配置几乎不可能一次正确（流体初始化、格式细节、湍流系数都容易出错）。ChatCFD 设计了迭代纠错循环（Iterative Correction of OpenFOAM Text，最多 30 轮）：

循环中还有两个精巧设计：错误重复检测（同一错误反复出现时升级处理策略，例如换参考案例或整体重写）和反思经验回放（把"为什么上一次修改无效"的分析结果注入后续提示词，避免在同一个坑里反复跌倒）。本轮复现在 NACA0012 案例中观察到该机制真实发挥作用：第 24 轮才修复 symmGaussSeidel 拼写错误后跑通。

五、端到端工作流程

  1. 输入：用户上传论文 PDF（或输入一句话描述）+ 网格文件（Fluent .msh 或 OpenFOAM polyMesh）；
  2. 案例提取：LLM 通读全文，按"几何 / 边界条件 / 流动参数 / 物理模型 / 求解器"的参数组合枚举所有可仿真的案例，编号为 Case_1、Case_2…；
  3. 对话选型：用户自然语言指定案例与求解器偏好，Agent 生成结构化配置（案例名 / 求解器 / 湍流模型 / 特殊物理模型 / 详细描述）并渲染为 Markdown 清单，可继续对话修改；
  4. 文件准备：网格转换（fluent3DMeshToFoam）并提取边界名称 → 按"求解器清单 + 湍流模型清单"确定文件全集 → RAG 检索论文获取边界条件与物理参数 → 逐文件生成 0/、constant/、system/ 全部配置；
  5. 运行与纠错：启动求解器，捕获报错进入 ICOT 循环（≤30 轮）；
  6. 输出：成功后保存时间步结果与运行日志到 run_chatcfd/，LLM 生成算例技术总结，用户可打包下载完整算例。

6.2 本地复现实测结果（Windows + WSL2 + OpenFOAM v2406）

✅ NACA0012 不可压案例——复现成功。完整流程：论文 PDF → RAG 边界条件提取 → 自动生成全部算例文件 → 网格转换 → simpleFoam（kOmegaSST）运行 → ICOT 自动纠错 24 轮后求解器正常收敛，输出 5 个时间步结果。纠错过程中修复了文件头格式、边界类型、离散格式拼写等多类错误，验证了循环的真实纠错能力。
❌ SERN 喷管可压缩案例——两次运行均失败（30 轮预算耗尽，卡在 thermophysicalProperties 结构错误）。这与论文自报的 30% 成功率一致——可压缩高温高压边界 + rhoCentralFoam 教程缺少湍流参考文件是主要难点，属于该系统的已知能力边界而非复现偏差。

复现过程中额外验证的工程发现：

  • 边界条件提取质量高：从喷管论文自动抽取的总压/背压/温度与论文表格逐位一致，且正确映射为 totalPressure / totalTemperature / waveTransmissive 类型；
  • 成本极低：两案例合计约 750 次 LLM 调用、156 万 token，使用国产模型（qwen-flash 兼容替代）成本可忽略；
  • 复现过程中修复了上游 6 处代码缺陷（配置字段过滤、JSON 双重编码、无操作笔误、混合模型思考模式超时等），流水线目前可在本地稳定运行；
  • 聊天界面已中文化并配深色主题，每个功能模块带说明，首屏加载约 30 秒。

七、局限与展望

  • 成功率与复杂度负相关：可压缩、多物理场耦合案例的成功率（30%）明显低于基础案例（82%），知识库对非常见求解器/湍流组合的参考覆盖不足；
  • 物理保真度验证自动化不足：能跑通 ≠ 物理正确（59% phy√），结果验证目前主要依赖人工；
  • 网格依赖用户：几何建模与网格划分仍需用户在外部完成，是自动化链条中未覆盖的一环；
  • 值得尝试的方向：为可压缩算例补充湍流参考知识、引入结果后处理与物理合理性自动校验、将嵌入模型换为中文增强模型以更好处理中文论文。
